# MVP مستقل آربیتراژ والکس / نوبیتکس

این پوشه یک مسیر اجرای مستقل برای پایش فقط‌خواندنی است؛ داده عمومی را می‌خواند، محاسبه paper انجام می‌دهد و تاریخچه را در SQLite ذخیره می‌کند. هیچ endpoint خصوصی، سفارش، برداشت یا انتقالی در این مسیر وجود ندارد. تنها ارتباط تلگرام، ارسال گزارش متنی وضعیت اسکن است.

## پیش‌نیاز
- Python 3.10 یا جدیدتر
- وابستگی‌های خارجی: `requests` و `python-socketio[client]` (برای آزمایش جریان زنده والکس).
- SQLite از کتابخانه استاندارد Python استفاده می‌شود.

## نصب و اجرا
از پوشه `arbitrage_mvp`:

```bash
python -m venv .venv
# ویندوز: .venv\\Scripts\\activate
# لینوکس/مک: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python run_scan.py
```

در ویندوز به‌جای `cp` می‌توان فایل `.env.example` را دستی به `.env` کپی کرد.

## واحد قیمت و تازگی داده
- طبق مستندات رسمی نوبیتکس، قیمت بازارهای ریالی در API بر حسب **ریال** است؛ بنابراین قیمت دفتر سفارش `IRT` برای مقایسه با قیمت تومان والکس باید بر ۱۰ تقسیم شود. مقدار پیش‌فرض `NOBITEX_IRT_PRICE_DIVISOR=10` همین تبدیل را انجام می‌دهد. منبع: https://github.com/nobitex/docs-api/blob/master/source/includes/_market_trade.md
- والکس بازارهای تومانی را با نمادهایی مانند `USDTTMN` منتشر می‌کند؛ `TMN` در اطلاعات دارایی والکس به تومان اشاره دارد. منبع: https://api-docs.wallex.ir/
- مستندات REST والکس برای `/v2/depth/all` زمان به‌روزرسانی هر دفتر سفارش را در ساختار پاسخ نمونه مشخص نمی‌کند. در نتیجه اسکنر فعلی زمان محلی دریافت را به‌جای زمان بازار نمی‌گذارد و فرصت فاقد timestamp معتبر را رد می‌کند.
- مستندات جدید والکس، پروتکل قدیمی Socket.IO/Engine.IO را برای پیاده‌سازی جدید کنار گذاشته و **Centrifugo** را معرفی می‌کند: `wss://api.wallex.ir/connection/websocket` با کانال‌های `orderbook:SYMBOL@buyDepth` و `orderbook:SYMBOL@sellDepth`. برای داده عمومی API Key لازم نیست.
- هر publication عمق بازار یک snapshot کامل است، اما عضویت در کانال snapshot اولیه نمی‌دهد. کانال عمق بازار تاریخچه، `offset`، sequence ID و timestamp سمت صرافی ندارد؛ پیام‌های ازدست‌رفته در زمان قطع اتصال نیز بازیابی نمی‌شوند. بنابراین حتی با اتصال موفق، timestamp دریافت محلی فقط زمان دریافت کلاینت است و برای تأیید هم‌زمانی بین صرافی‌ها کافی نیست.
- زمان سمت سرور نوبیتکس از `lastUpdate` خوانده می‌شود؛ اگر زمان وجود نداشته باشد یا قدیمی باشد، سیگنال رد می‌شود.

## تنظیمات حساس
- کارمزدها، لغزش و هزینه انتقال از متغیرهای محیطی خوانده می‌شوند؛ مقادیر نمونه، کارمزد واقعی صرافی نیستند.
- تا وقتی `FEES_CONFIRMED=true` و `TRANSFER_COST_CONFIRMED=true` نشده‌اند، فرصت‌ها واجد شرایط اعلام نمی‌شوند.
- هزینه انتقال فعلاً فقط یک فرض درصدی برای شبیه‌سازی است؛ تا زمانی که شبکه، کارمزد برداشت/واریز و امکان انتقال دارایی تأیید نشده‌اند، نتیجه سود قطعی نیست.
- نماد مشترک به‌تنهایی اثبات‌کننده یکسان بودن دارایی یا شبکه انتقال نیست.

## داده و تاریخچه
فایل `arbitrage_history.sqlite3` به‌صورت خودکار ساخته می‌شود. جدول‌های `scans` و `opportunities` زمان اسکن، شمار دفترها، تنظیمات، فرض‌ها، سود تخمینی و دلیل رد هر مسیر را نگه می‌دارند.

## امنیت و دامنه
در این MVP هیچ کلید API لازم نیست. هیچ کد سفارش‌گذاری/برداشت/انتقالی در این پوشه قرار ندارد. این پروژه ابزار آزمایش و ثبت فرضیه است، نه سامانه آماده معامله.

## بررسی فرادادهٔ زمان دفتر سفارش REST

اسکریپت `wallex_depth_metadata_probe.py` دو endpoint رسمی `/v1/depth?symbol=USDTTMN` و `/v2/depth/all` را فقط‌خواندنی بررسی می‌کند. این آزمایش نام فیلدهای timestamp/sequence را در نمونهٔ پاسخ و هدر HTTP `Date` ثبت می‌کند. هدر `Date` فقط زمان پاسخ HTTP است و **هرگز** به‌عنوان زمان به‌روزرسانی دفتر سفارش استفاده نمی‌شود. خروجی این probe صرفاً تشخیصی است و به اسکنر یا شرط پذیرش سیگنال متصل نیست.

اجرای محلی:
```bash
python wallex_depth_metadata_probe.py
```

## آزمایش جریان زنده والکس (Centrifugo؛ تشخیصی، نه سیگنال)

مستندات فعلی:
- اتصال: `wss://api.wallex.ir/connection/websocket`
- کانال خرید: `orderbook:SYMBOL@buyDepth`
- کانال فروش: `orderbook:SYMBOL@sellDepth`
- پیام نخست `connect` است؛ سپس برای هر کانال `subscribe` جداگانه ارسال می‌شود.
- در کلاینت بدون SDK باید هر ۲۵ ثانیه به پیام ping خالی `{}` با همان `{}` پاسخ داد.
- برای کانال‌های عمق، پاسخ subscribe خالی است و snapshot اولیه ندارد. publicationهای بعدی snapshot کامل‌اند اما timestamp و offset ندارند.

اجرای probe فقط‌خواندنی:
```bash
python wallex_centrifugo_probe.py
```

اسکریپت `wallex_centrifugo_probe.py` فقط handshake، عضویت، دریافت publication و وجود احتمالی فیلدهای زمان/توالی را گزارش می‌کند. به scanner و شرط پذیرش سیگنال متصل نیست. تست‌های قبلی Socket.IO/Engine.IO در CI صرفاً برای ثبت نتیجه مسیر قدیمی باقی مانده‌اند و مسیر مستند جدید نیستند.

منابع رسمی:
- https://developers.wallex.ir/docs/socket-intro
- https://developers.wallex.ir/docs/socket-raw-protocol
- https://developers.wallex.ir/docs/socket-buy-depth
- https://developers.wallex.ir/docs/socket-sell-depth

## پایش خودکار و گزارش تلگرام
- گردش‌کار `.github/workflows/arbitrage-monitor.yml` علاوه بر پایشگر قبلی، job مستقل `read-only-mvp` را اجرا می‌کند.
- اجرای زمان‌بندی‌شدهٔ فعلی از طریق فراخوانی `workflow_dispatch` توسط زمان‌بند موجود انجام می‌شود؛ job جدید دفتر سفارش عمومی را می‌خواند و گزارش وضعیت را به همان مقصد تلگرام تنظیم‌شده در GitHub Secrets می‌فرستد.
- نام secretها فقط `TELEGRAM_BOT_TOKEN` و `TELEGRAM_CHAT_ID` است. هیچ توکنی داخل کد یا فایل مخزن قرار نمی‌گیرد.
- تاریخچه SQLite در اجرای GitHub Actions با Cache نگهداری می‌شود؛ اجرای محلی نیز فایل SQLite پایدار روی دستگاه می‌سازد.
- اگر timestamp معتبر والکس در دسترس نباشد یا API خطا بدهد، گزارش وضعیت و علت رد فرصت ارسال می‌شود؛ هیچ سیگنال نامعتبر به‌عنوان فرصت سودآور معرفی نمی‌شود.
- برای اجرای محلی گزارش: `python run_monitor.py`. در صورت تنظیم متغیرهای تلگرام، گزارش ارسال می‌شود؛ در غیر این صورت فقط در ترمینال چاپ خواهد شد.


## پایش دو‌سطحی (افزوده‌شده)

- `scanner.py` مسیر تأییدی قبلی است و بدون timestamp معتبر سمت هر دو صرافی، هیچ سیگنال واجدشرایطی تولید نمی‌کند.
- `potential_scanner.py` یک مسیر جدا برای کشف سرنخ‌های احتمالی است. دو درخواست REST را هم‌زمان اجرا می‌کند و برای هر پاسخ `request_started_at_utc`، `received_at_utc`، `received_monotonic_ns` و مدت درخواست را ثبت می‌کند.
- `received_at_utc` صرفاً زمان دریافت کلاینت است. فیلد `exchange_timestamp` فقط از خود payload استخراج می‌شود و در نبود آن `null` می‌ماند. زمان دریافت، زمان معامله، HTTP Date و زمان ایجاد بازار هرگز جایگزین timestamp دفتر سفارش نمی‌شوند.
- مسیر احتمالی فقط وقتی اختلاف زمان دریافت دو پاسخ حداکثر ۵ ثانیه و مدت هر درخواست حداکثر ۱۰ ثانیه باشد، در گزارش به‌عنوان سرنخ با کیفیت انتقال نمایش داده می‌شود. این کنترل‌ها stale بودن داده در سمت صرافی یا هم‌زمانی واقعی را ثابت نمی‌کنند.
- خروجی احتمالی همیشه `verified=false`، `eligible=false` و `execution_allowed=false` دارد؛ از شمار سیگنال‌های تأییدشده جداست و فقط برای پژوهش/پایش است.
- هر دو مسیر همچنان فقط GET عمومی دارند. هیچ endpoint خصوصی یا کد سفارش‌گذاری اضافه نشده است.
- تست ایمنی: `python -m unittest -v test_mvp.py test_wallex_stream.py test_monitor.py test_potential_scanner.py`
